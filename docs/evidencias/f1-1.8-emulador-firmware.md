# Evidência 1.8: firmware ESP32 rodando no QEMU da Espressif contra o broker local

- Data: 2026-11-15. Tarefa 1.8 do PLAN; RF-G-05, RF-A1-02 ("execução em emulador"); decisão no ADR-0021 (Proposto).
- Máquina: WSL2 (Ubuntu 26.04), sem sudo. Broker da base em `localhost:1883` (perfil reduzido, ADR-0016).
- **Natureza dos dados:** o firmware é o real (`hardware/firmware`), mas botão e temperatura vêm de estímulo
  sintético da bancada virtual (`bancada/demo.txt`). Nada aqui é medição (ADR-0013); `dur_s` reproduz os
  intervalos escritos no arquivo de estímulo.

## 1. Emuladores avaliados

| Opção | Resultado | Comando / observação |
| --- | --- | --- |
| QEMU da Espressif `esp-develop-9.2.2-20260417` | **Funcionou** | Tarball oficial, sha256 `0eecb2a3…a547e35`. `ldd` acusou `libSDL2-2.0.so.0` e `libslirp.so.0` ausentes; resolvido com `apt-get download libslirp0 libsdl2-2.0-0 libsdl2-classic libsamplerate0 libxss1 libdecor-0-0` + `dpkg-deb -x` para `~/.local/opt/qemu-esp-develop-9.2.2-20260417/libs` (sem instalar). `qemu-system-xtensa --version` → `QEMU emulator version 9.2.2 (esp_develop_9.2.2_20260417)`; `-machine help` lista `esp32`; `-nic model=help` → `open_eth` |
| Wokwi CLI 0.29.1 | **Não executado** | Binário `wokwi-cli-linuxstatic-x64` baixado; `--version` → `0.29.1 (0aa185144b92)`. A simulação roda no serviço da Wokwi e exige `WOKWI_CLI_TOKEN` (conta). Não criei conta nem enviei o firmware ao serviço; a tentativa de rodar foi bloqueada pela política de permissões desta sessão. Pendência do grupo |
| `native` como "firmware em processo" | Não necessário | O QEMU funcionou; `native` não emula a placa |

Problemas no QEMU e solução (detalhe no ADR-0021):

1. Arduino-ESP32 2.0.17 sai com `# CONFIG_ETH_USE_OPENETH is not set` (`tools/sdk/esp32/sdkconfig`); o QEMU não
   emula Wi-Fi. → driver `esp_eth_mac_openeth.c` do ESP-IDF v4.4.7 (`38eeba213a`) copiado sem alteração para
   `src/qemu/openeth/`, compilado só no ambiente `esp32-qemu`.
2. Primeiro boot sem `wdt_disable`: dois resets espúrios antes de estabilizar (saída real):
   ```
   rst:0x8 (TG1WDT_SYS_RESET),boot:0x12 (SPI_FAST_FLASH_BOOT)
   rst:0x7 (TG0WDT_SYS_RESET),boot:0x12 (SPI_FAST_FLASH_BOOT)
   ```
   Com `-global driver=timer.esp32.timg,property=wdt_disable,value=true`, duas execuções seguidas deram
   `rst:0x1 (POWERON_RESET)` direto, `boot 1` e depois `boot 2` (NVS preservada).

## 3. Execução gravada (firmware no QEMU → broker → gravador)

Comandos (pasta `MOD 3`):

```bash
uv run --project hardware/emulador python -m emulador.gravador --saida dados/amostras/f1-firmware-emulado.jsonl \
    --duracao 80 --filtro 'dev/v1/esp32-bat01/#' --meta fonte=firmware:emulado ... &
(cd hardware/firmware && ./emular.sh --estimulo bancada/demo.txt --duracao 65)
```

Gravador: `gravadas 17 mensagens (0 inválidas)`. Serial do ESP32 emulado (trecho real):

```

[rede] ethernet openeth (QEMU) iniciada; aguardando DHCP
[rede] eth ip 10.0.2.15
[mqtt] conectando (boot 4)
[mqtt] conectado
[bancada] temperatura 24.6
[bancada] toque 1
[bancada] toque 2
...
[bancada] temperatura nan
[sensor] leitura de temperatura falhou; nada publicado
[bancada] toques 4 temperatura 25.0

```

O filtro foi `dev/v1/esp32-bat01/#` e não `dev/v1/#`: numa primeira gravação com `dev/v1/#`, o broker

pela execução anterior do firmware (Last Will); o conferidor só considera o que vem depois do status `online` com
`origem` = `firmware:emulado`.

## 4. Validação pelo contrato e comparação de formato com o emulador Python

`uv run --project hardware/emulador python -I hardware/firmware/scripts/conferir_formato.py
dados/amostras/f1-firmware-emulado.jsonl dados/amostras/f1-emulador-roteiro.jsonl --id esp32-bat01` (saída 0):

```
mensagens do firmware (firmware:emulado) em f1-firmware-emulado.jsonl: 16
  ok  status online          valido=True  forma=igual {"v":"online","fw":"0.1.0","boot":4,"origem":"firmware:emulado"}
  ok  evt ciclo inicio       valido=True  forma=igual {"seq":0,"up_ms":9092,"boot":4,"fase":"inicio"}
  ok  tel temperatura        valido=True  forma=igual {"seq":1,"up_ms":10000,"boot":4,"v":24.6}
  ...
  ok  evt ciclo fim          valido=True  forma=igual {"seq":4,"up_ms":21110,"boot":4,"fase":"fim","dur_s":12.018}
  ...
  ok  evt ciclo fim          valido=True  forma=igual {"seq":9,"up_ms":36652,"boot":4,"fase":"fim","dur_s":9.516}
  ok  tel temperatura        valido=True  forma=igual {"seq":10,"up_ms":45003,"boot":4,"v":25}
  ...
  ok  status last-will       valido=True  forma=igual {"v":"offline"}
tipos no firmware: {'status online': 1, 'evt ciclo inicio': 2, 'tel temperatura': 10, 'evt ciclo fim': 2, 'status last-will': 1}
resultado: OK
```

- 16 de 16 mensagens do firmware válidas por `contrato.validar`; mesmas chaves, mesma ordem e mesmos tipos JSON
  das mensagens do emulador Python, por tipo de mensagem.
- `seq` 0 a 13 sem lacuna, um contador para tel e evt; nenhum campo de data/hora.
- `temp nan` → nenhuma telemetria entre `up_ms` 36 652 e 45 003 (a amostra de 40 000 não saiu).
- `v: 25` (inteiro) no firmware contra `25.0` no Python: mesmo número em JSON, aceito pelo contrato
  (`tel-valor-inteiro.json`). Diferença conhecida da 1.7.
- Last Will: o QEMU foi morto pelo `timeout` (queda, sem DISCONNECT); o broker publicou `{"v":"offline"}` às
  23:50:18.715, 4 s depois da última telemetria (23:50:14.678): ao morrer, o QEMU fecha o socket do slirp e o
  broker vê a queda sem esperar o keepalive. Uma assinatura nova depois do fim recebeu
  `retido: True dev/v1/esp32-bat01/status {"v":"offline"}`. O emulador Python usa a mesma constante
  (`contrato.LAST_WILL`); o "offline gracioso" com metadados do Python não tem par no firmware (placa não desliga
  de forma graciosa).
- Limite da comparação: o gravador guarda o payload já decodificado; a validação usa o JSON compacto remontado, não
  os bytes originais.

## 6. Modo interativo e NVS

- `./emular.sh --sem-compilar` num pseudo-terminal (`script`), digitando `estado` + Enter e `Ctrl-A X`:
  `[bancada] toques 0 temperatura nan`, `QEMU: Terminated`.
- A imagem de flash foi movida para `hardware/firmware/.qemu/` (fora do Git) depois que um `pio run` com flags
  diferentes apagou `.pio/build` inteiro e, junto, a NVS (o `boot` voltou a 1). Com a imagem nova: `boot 1` e, na
  execução seguinte, `boot 2`. A gravação da seção 3 foi feita antes dessa mudança (imagem em `.pio/build`); o
  script final foi exercitado nas seções 5 e 6.

## 7. Limitações (limitação → impacto → proposta)

- Rede Ethernet no lugar do Wi-Fi → reconexão de Wi-Fi não exercitada → testar em placa ou no Wokwi (exige conta).
- Botão e DHT22 pela serial → GPIO e protocolo do DHT22 não exercitados; o repique simulado é um padrão fixo →
  testar em placa.
- Watchdogs dos timer groups desligados no QEMU → travamento que dispararia o watchdog não aparece → manter teste de
  placa no checklist.
- Firmware emulado e emulador Python usam o mesmo id `esp32-bat01` com contadores de `boot` independentes → o
  gateway pode ver `boot` voltar atrás ao alternar as fontes no mesmo id → na troca de L0 (tarefa 1.10), rodar uma
  fonte de cada vez e registrar a sessão.
